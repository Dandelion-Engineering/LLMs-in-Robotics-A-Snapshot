# Operator recovery boundary and source review

This is a source-level assessment. Runtime acceptance is determined by immutable qualification/audit/preparation receipts; this document does not claim that those jobs passed.

The original frozen `recovery.prepare_recovery` performs preparation and deliberately restricts destination storage to D:. Its official preparation path additionally expects `pair/recoveries` and the original pair's active-lineage pointer. Session 59 moved only the writable Maps instance to C:, retaining the original D: pristine start and publishing a separate storage-route authority. Consequently the original Maps lineage pointer still describes the pristine D: archive. Calling frozen recovery with C: is expected to fail. The qualification records that rejection without editing its code, imports, certificate or path resolution.

The frozen launch path is separate: `run.verify_run` calls the unchanged `check_branch_authority`, checks exact source/configuration/schedule identity, commissioning certificate, installed environment, and the completed matched Baseline. It does not impose the D: preparation restriction. The normal resumed controller then verifies checkpoint content, event-chain tail/byte length, replay index, filesystem and full inode namespace before restoring the world. This separation permits a newly authorized operator preparer, subject to actual qualification; no source transition is implied.

`prepare_branch.py` implements only the authorized C: branch construction. Its production destination is fixed to `Local Experiment Data/apartment-v4-maps/recovery-session63/recovered-run`. It requires a new non-aliased path, the authentic failed/retired parent, exact checkpoint-5 hashes, the original C: storage-route binding, unchanged source identity and the prospective frozen recovery policy. The actual exclusive claim uses the original pair's ordinary `recovery-claims/<parent branch id>` directory. Atomic directory creation refuses both duplicate and previously interrupted preparation. Faults retain their claim and failed destination; no rollback erases evidence.

Data copied to the branch are restricted to the checkpoint filesystem/current content objects/inodes, bounded event/replay/sensor prefix, and accepted sessions 1-5 with their before-filesystem mirrors. All five accepted checkpoints are copied; the frozen preparer would copy only the latest. No abandoned session-6 evidence is copied. Original absolute references inside historical receipts stay byte-identical and resolve to the preserved parent. This distinguishes provenance references from the branch's actual writable paths.

Branch `run.json` changes only the branch ID and addition of explicit recovery provenance. Configuration, schedule, source identity, paired root, template, model, report rules and guest-visible files remain exact. `latest-checkpoint.json` points to the copied checkpoint. `recovery-ready.json` and append-only claim records identify the operator policy, parent inventory, authority and one abandoned model call. These are operator files outside the guest filesystem.

Qualification fixtures live only under `qualification001`. Their official metadata is used to exercise the real unmodified official verifier without launching them. They are not authorized scientific continuations. Actual controller/native-mount/transport tests use a separate disposable copy, with no provider call and no writes to the accepted candidate or failed parent. Corruption cases retain the before/rejected byte samples and exact rejection traces; restored fixture bytes are reverified. Actual production submission is available only in `launch_continuation.py`, which requires all three successful terminal gates, route hashes and the fixed destination.

`audit_recovery.py` independently constructs the expected data inventory from original parent/checkpoint bytes, allowing only three known metadata files to differ. It independently replays journals and restores world state, checks successful and rejected fixtures, and reauthenticates unchanged official checks. Actual preparation compares every scientific/data byte with that audited candidate and rereads the production claim, pointer and identity before appending the original pair's lineage transition. Prior lineage bytes are retained; the historical D:-to-C: transition is explicitly bound to Session 59, never retroactively represented as a frozen recovery.

No scientific-code patch, monkeypatch, module replacement, drive alias, certificate fabrication, relaxed validator, direct parent resume, new matched pair, schedule reroll or guest coaching is part of this route. A failing critical gate leaves the continuation unlaunched and requires a decision-ready report. These controls are trusted operator procedures, not a claim that the frozen runner's small branch-binding check independently enforces every preservation condition.
