# Workspace startup and cleanup review

This is a Development Codex source review and a separately implemented evidence-reader design. It is not an external reviewer or another model's certification. The executable audit is `audit_workspace.py`; its terminal receipt decides whether the engineering result qualifies.

## Original failure mechanisms

The original `Workspace` restored every regular inode before the first journal record and before FUSE registration. Its caller waited only 20 seconds for a mount. Checkpoint 14 contains 393 namespace entries, 362 regular inodes, 358 unique content objects and 51,034,996 logical bytes. In the profiled original implementation, publishing content took 20.03 of 21.19 restore seconds in the checkpoint-size advised-cold case; `_publish` accounted for 18.98 seconds. These are nested times, not additive costs. Open/close/replace and flush operations across the Windows filesystem bridge dominate the measured profile. This reproduces exceeding the original gate, not the exact storage/cache conditions of Session 37.

The constructor launched the service and then raised before `run.py` assigned the object. The test-only delayed service reproduced an orphan while the caller still held `None`. The original control thread also remained available after `destroy()` closed the journal. Holding that post-destroy interval open reproduced its attempted append and `I/O operation on closed file`. Both reproductions use isolated state and retained original source; no official receipt was changed.

## Repair and boundaries

`run.py` now allocates the workspace before calling `start()`. Legacy constructor callers also receive ownership through an exception attribute, with cleanup inside `start()`. Admission-receipt publication belongs inside that guard: source review found that an exception in a final `save()` could otherwise reproduce the original ownership bug after a successful mount. The final matrix injects that failure. Linux ownership is published before service imports and carries run ID, mount, PID, start ticks and boot ID. A prepublication bootstrap can be identified only by its exact unique argument tokens; broad kills are never used.

Preparation runs in an owned Windows worker and emits a durable append-only progress log. The reader consumes a bounded complete tail. This avoids replacing an open progress file on the actual exFAT volume. Earlier replacement failures remain in qualifications 003 and 004; delete sharing alone did not resolve them, and no exact outside handle owner was established. Linux progress snapshots live on its native filesystem. Only an ordered phase change or completed file/byte counters renew the no-progress budget; sequence numbers and timestamps alone do not.

Defaults are a 20-second no-progress bound and a shared 120-second startup budget. Preparation consumes that same total budget. Helper setup receives the remaining budget, and the Windows caller checks its own elapsed time before service launch and after readiness/admission publication. Qualification008 forces a helper-setup overrun and verifies rejection with no native service started. The native readiness fence requires initial journal commitment, FUSE initialization, mount-table presence, a healthy identity-bound socket response and a bounded successful FUSE stat. Child exit, stalls and absolute expiry remain failures. Test-only shorter policies exercise failures without long hangs; they do not alter an official configuration.

Native Windows I/O prepares exactly the existing chunk/descriptor format. Every stored file is flushed before handoff. Linux adopts the prepared directories into its newly created unmounted journal, flushes the adopted object and chunk directories as well as both affected parents, checks storage accounting and independently verifies the reconstructed size and SHA-256 of every restored inode before the initial journal record. Source review added those explicit child-directory flushes after qualification006/audit001; qualification007 injects failure at that boundary. The existing reader and content format are unchanged. Partial preparation/adoption cannot become a ready workspace. The old direct restore path remains readable but is not the new Windows caller's path.

Normal close first verifies no open guest handles, unmounts, waits for actual process retirement and verifies the final journal/native exit before exporting state. There is no required post-unmount request. Compatibility retirement requests observe lifecycle state without appending. Checkpoints after close are rejected under the same lock used by `destroy()`. Abnormal cleanup may signal only an authenticated owned process, has bounded waits and explicitly remains `passed=false`. Failed startups never become normal experimental sessions.

## Independent checks and limits

The audit uses the unchanged pre-repair journal reader, exact manifests and queue receipts. It checks every matrix case, retained failures, source/environment identity, namespace/hard-link/symlink/mode restoration, writes after restoration, actual open-handle rejection, corruption after preparation, a hang before owner publication, poisoned-journal rejection, current process/mount absence and exclusive Windows opens of retained logs. It then recomputes the entire official v2/v3 inventory and independently validates checkpoint 14 and its prefix. The original false retirement and unchanged recovery guard remain explicit checks.

This is bounded software qualification on the current desktop and D: volume. Cache eviction is advisory; device-cold behavior and statistical performance generalization are not established. Power loss, kernel failure, forced termination of the supervising Windows process and arbitrary storage hangs are outside the exercised failure set. Missing or failed cleanup evidence remains a failure, even if later readback establishes retirement. No model, controller experiment, official recovery, condition launch, monitoring automation or condition comparison is part of this session.
