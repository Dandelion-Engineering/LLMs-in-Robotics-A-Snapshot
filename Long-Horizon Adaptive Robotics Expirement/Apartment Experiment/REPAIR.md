## Measured cause

Queue `20261007T045828061579Z-37c81eac` ended with integer exit 1 at 05:33:56 UTC on October 7 (22:33:56 PDT October 6). The native turn reached `completed`, but native cleanup did not qualify. There was no clean filesystem closeout or checkpoint. This is not a measured task endpoint.

The inherited journal wrote a full, content-addressed file version on every successful FUSE write. Content addressing deduplicates identical files; it does not deduplicate growing prefixes. Robot Codex's append-only log therefore produced quadratic storage growth.

The separate parent transport ledger reached 1,048,283 bytes against its 1,048,576-byte ceiling. Its 2,260 per-frame records accounted for 1,040,445 bytes. It records opaque frame sizes/hashes, not workspace file snapshots. It therefore has an independent growth mechanism. Error reporting hit the same ceiling during native cleanup/drain and masked the earlier failure; the 25-second transport drain timeout was not the 7,200-second model wall limit.

A fresh inspection also found the poisoned FUSE service still mounted. `Workspace.close()` had raised on the clock-bridge error before reaching unmount/retirement. After preserving its process identity, six transient control files, original manifest and console bytes, session 30 unmounted that exact namespace and sent SIGTERM to the verified PID/start-tick/command-line identity. It did not create a final journal record or checkpoint. Only the console log acquired cleanup diagnostics; the pre-cleanup bytes are retained separately and the final readback checks every other original file.

## Intended-duration implications

These are conditional projections, not observations or storage guarantees. If the measured append pattern continued at the same rate, one 1,800-second throwing log would retain approximately 4.96 GB of full versions, already beyond the old 3 GiB journal limit. Resetting the log each session and assuming only seven throwing plus fourteen household windows gives approximately 35.95 GB of object versions per condition, excluding return/closeout and repeated incomplete household sessions. Reusing one growing log across those 15,960 working seconds would instead project approximately 389.93 GB because of quadratic prefix copying.

The experiment does not bound the number of household sessions needed for success. Neither those projections nor commissioning can guarantee eventual completion. The repair removes the demonstrated amplification; it retains explicit finite limits and visible failure rather than assuming unlimited storage or task success.

## Repair and evidence semantics

`content_store.py` preserves the full-file SHA256 used by each namespace version. Small writes retain immutable, losslessly compressed content chunks and a delta descriptor. At most 32 deltas separate a version from a chunked snapshot; snapshot chunks are shared by content hash. Full rewrites and large changes use snapshots directly. Every mutation still publishes durable content before its hash-chained journal record and before replying to the guest. No journal event or intermediate file version is coalesced away.

`journal_reader.py` streams the journal, checks its chain, state transitions, reads and every distinct content version. It avoids keeping a complete namespace copy for every mutation. The viewer reads both historical raw objects and new descriptors and keeps the same measured cross-clock visibility rule. Final exports and checkpoints still contain exact regular-file bytes plus the full Linux inode namespace, modes, timestamps, links and empty directories.

Transport frame accounting now uses ordered SHA256 commitments, frame counts and byte totals for each direction. Both endpoints independently accumulate every original frame descriptor; their terminal commitments must match. Lifecycle events, native ownership, channel authentication, H2 state, queue ceilings, cleanup barriers and drain/retirement gates remain. Individual per-frame metadata rows are no longer retained in repaired runs; existing observable tool, request, sensor and native lifecycle evidence remains. Commitments establish transcript equality, not recoverability of each frame descriptor.

The first repaired live attempt uncovered a further transport failure at 1,509.48 simulation seconds. Its journal and compact metadata remained well below their limits, but the parent receive loop failed with `ValueError` at a recorded peak of 393,216 queued bytes plus 655,360 bytes of fixed framing headroom: exactly the unchanged 1 MiB channel ceiling. The inherited receive path tried to reserve the next DATA frame immediately. The retained exception omitted its message, so queue saturation is the diagnosis supported by that peak, the failing code path and a separate exact reproduction; it is not a recovered original error string.

The prospective receive adapter waits for capacity before consuming DATA payload bytes and hands its reservation synchronously to the original receive loop. Namespace upload/download paths also wait within the existing queue limits. Cancellation releases its own reservation. No payload is changed or retried, no queue or drain limit is enlarged, and exact receive-error detail is now retained if another failure occurs.

The next live attempt passed the full 1,800-second work window, then stopped before docking at a separate inherited **32 MiB cumulative app-server output limit**. The client initiated interruption and forced exit; the reported socket reset followed that exit. Its retained native event log was 33,672,542 bytes, including 30,532,491 bytes of completed image-tool records (75 records, mostly image-result echoes). The compact transport ledger was only 29,689 bytes after failed cleanup, its peak queue plus headroom was 917,504 bytes, and executor capture was 2,020,644 bytes. There was no new filesystem or transport-metadata exhaustion. `operations/session-30/live002-failure-diagnosis.json` records this causal order and the terminal state.

`native_stream.py` separates a single message from cumulative recording and buffered memory. It retains the original observable-event filtering, redaction and durable log format. Ordinary notifications are released from memory after logging; only at most four turn-completion notifications are retained for native control. The input queue has an 8 MiB / 256-item ceiling, allowing one individually bounded message to occupy an empty queue. Two reader threads and JSON parsing have their own transient allocations; this queue figure is not a total-process memory bound. Producers wait for capacity rather than dropping records. Actual stream-reader retirement and exact retained-event byte counts are recorded and checked.

| Native-client limit | Prospective value and reason |
|---|---|
| Individual input message | Original 32 MiB limit retained. |
| Total input per native session | 256 MiB; explicit finite allowance for the long apartment session. |
| Retained observable event log | 512 MiB; separate cap including serialization/receipt overhead. |
| Cleanup input | Separate 4 MiB allowance; exhaustion cannot prevent reading the ordinary cleanup handshake. |
| Native graceful / absolute retirement deadlines | Original 5 / 10 seconds retained. |

The cumulative allowance increase is based on observed linear image-result traffic, with memory buffering repaired separately. At the failed session's approximately 32 MiB per 31.5 minutes, the original 120-minute model wall limit projects approximately 122 MiB of input. The 256 MiB cap provides roughly a factor of two over that conditional projection; it is not a guarantee for arbitrary future verbosity. The finite event cap, D: admission check and explicit failure behavior remain. No image result is silently discarded. The executor capture's unchanged 64 MiB cap was approximately 32 times its observed size here. H2's 1,024-stream bound limits active streams and retained recent close proofs; it is not a 1,024-request lifetime limit. Its fixed queue, control-record and metadata limits remain in force.

If evidence recording itself fails, the transport marks the run invalid and continues teardown. A failed journal uses an explicit identified-service retirement path; it cannot be promoted to a successful checkpoint. The original 3 GiB journal, 16 MiB file and 256 MiB live namespace limits remain. A new native session is refused below 20 GiB free on the evidence volume. Both official conditions receive the same repair.

The third live attempt exposed an ordinary HTTP/2 cancellation race. Stream 369 received an upload `RST_STREAM` with code 8 (CANCEL), then response headers already in flight arrived. The inherited passive witness deleted the stream state at cancellation and rejected those headers with the exact error `HTTP/2 headers on unavailable stream`. Its native stream was only 10,094,423 bytes, its queue plus headroom peaked at 917,504 bytes, and the native reader reported no errors. This was a separate protocol-observation failure. See `operations/session-30/live003-failure-diagnosis.json`.

[RFC 9113 sections 5.1 and 6.4](https://www.rfc-editor.org/rfc/rfc9113.html#section-5.1) require a canceling endpoint to handle frames already in flight. `h2_runtime.py` retains a bounded proof for each pre-cleanup client CANCEL on an already opened stream, allowing the original parser to process later response frames. It preserves exact cancellation bytes/positions, per-stream ordered wire commitments, raw reset/normal-close counts and local observation order. The added record bound is 64 per channel; existing control/metadata limits remain. Server resets, other error codes, unknown/reused streams, duplicates, malformed framing and incomplete retirement still fail. No payload is changed, replayed or dropped by this adapter.

`h2_readback.py` separately checks those proofs and the inherited authenticated cleanup proofs, accounts for every raw reset, and reconciles both endpoints' byte/structure facts. A response can finish at one observer before the cancel reaches it and finish later at the other observer; the raw classifications remain in the artifacts. Each accepted cancellation must still have the same opening, cancel bytes, final wire commitments and completion facts at both endpoints. Reconciliation is enforced before transport qualification and again during independent session readback. The original frozen campaign implementation remains byte-identical.
