# B01-A2-r1 — Guarded Procedure Composer

**Status: proposed design.** This is Batch 01's procedure-generation candidate. There is no implemented interpreter, running model, frozen executable or measured result attached to this revision. The [Shared Implementation Contract](../../Batch%2001/Shared%20Implementation%20Contract.md) supplies common resources and implementation gates; the experiment's [Contract](../../Long-Horizon%20Adaptive%20Robotics%20Experiment%20Design/Contract.md), [Evaluation](../../Long-Horizon%20Adaptive%20Robotics%20Experiment%20Design/Evaluation.md) and [Evidence](../../Long-Horizon%20Adaptive%20Robotics%20Experiment%20Design/Evidence%20and%20Investigation.md) remain authoritative.

## Contribution and complete loop

The LLM authors a bounded reactive procedure: explicit sequencing, observation-dependent branches, waits and guarded actions. A deterministic interpreter executes that procedure without requiring an LLM call for each primitive action. Unlike a task/skill dispatcher, the model supplies the control flow that connects several observations and actions. Unlike the objective composer, it changes procedure structure rather than a numerical motion objective.

The loop is: current order and observations → retrieve consequential records → generate a typed procedure → validate → execute one bounded step → acquire feedback and verify relevant physical conditions → checkpoint → continue, repair or request help. The initial procedure can cover a small job segment, such as processing and inspecting one part. It need not fit an entire extended episode into one model response. The interpreter has no concealed plan that completes the job if synthesis fails; it may observe, reconcile already dispatched work and hold safely while requesting a replacement procedure.

The planned common text model is **Qwen3-4B-GGUF, official Q4_K_M, with thinking disabled**, subject to local resource, artifact and terms verification. It is not installed or frozen by this proposal. Each call has a 16,384-token total context ceiling, including at most 1,024 output tokens. Exact weights, quantization, runtime, generation settings and prompt bytes must be recorded before implementation is frozen. No paid or remote fallback is assumed. Model failure produces explicit timeout/invalid-output evidence rather than an invented procedure.

## Inputs, state and model context

The candidate receives the common visible-image-derived tag detections with acquisition time, covariance and visibility; public depth/geometry estimates; joint/gripper feedback; current device I/O; current order and amendments; and its own bounded command receipts. A shared deterministic scene adapter turns these into text and typed values. No simulator inventory, hidden process history, contact identities or evaluator log enters that adapter. The text model does not itself inspect RGB images in this revision. Its information limitations are those of the declared adapter and public sensors.

The prompt includes the effective order, current procedure version and checkpoint, relevant public state with ages, unresolved requests, conflicting observations, and bounded excerpts of previously verified procedures or corrections from this episode. Retrieval records identify the actual bytes and versions supplied. Context packing first preserves current order and unresolved consequential work; overflow is reported and uses a smaller procedure segment, not silent truncation of a material contradiction. A recorded confidence phrase does not authorize action: guards operate on observable conditions and explicit unknowns.

State has separate intent, observed/inferred condition, dispatch, terminal feedback and verified-outcome fields. For example, a successful `place` transport response does not establish that the part remains in the tray. A candidate-visible verification may remain uncertain even if the evaluator privately knows the answer.

## Typed procedure and execution authority

The generated artifact is data in a small declarative language, not Python, shell, executable expressions or imports. Proposed node types are bounded sequence, branch on an approved predicate, request fresh observation, await public event with deadline, invoke approved motion/station operation, record evidence reference, bounded retry, and request help. Predicates use an enumerated vocabulary, typed arguments and three-valued results: true, false or unknown. Unknown cannot pass a positive eligibility or completion guard.

Each procedure declares its order version, required evidence freshness, node identifiers, resource use, maximum transitions and retry counts. Static validation rejects unknown operations, invalid references, cycles without finite bounds, unsupported parameters, quota excess and missing failure exits. Runtime validation repeats the relevant order, sensor-age, precondition and ownership checks immediately before dispatch. Validation establishes admissible syntax and permissions, not successful manipulation or a correct overall plan.

Approved calls use the common grasp/place/inspect wrappers, Cartesian/path services and station API. All other entrants may use the same services. The common executor produces bounded trajectories; the shared actuator layer applies the same limits and interlocks. The interpreter cannot alter protected limits, recipes or eligibility. It cannot read files except through the declared candidate store or perform network/process operations. Its implementation must still undergo adversarial boundary tests; using a DSL alone does not prove isolation.

Commands carry unique request and runtime-incarnation IDs, parent procedure/node IDs, order version and deadlines. Receipts, accepted execution and physical evidence remain separate. A retry of the same request ID queries the original dispatch result within the public receipt window; it is not a new action. Every deliberate new consequential attempt gets a new ID with a reason and parent relationship.

## Timing, online repair and uncertainty

Physics and machine timers continue during generation and disk writes. At most one procedure controls a resource. Accepted arm commands expire within two seconds unless reauthorized. The local interpreter can renew a bounded operation while a model call is pending only if its live guard, evidence freshness, resource lease and current order still permit that operation. This renewal logic is explicit candidate code and its work counts toward runtime cost. It cannot use renewal to execute an unbounded stale plan.

A relevant amendment, failed guard, unresolved action or unexpected physical observation suspends the affected branch. Disjoint already-authorized activity may continue if its eligibility remains valid; otherwise the executor acknowledges cancellation and enters the common hold/brake behavior. The model receives the smallest supported discrepancy and can propose a replacement procedure. Replacement is validated and committed as a new version, then activated at an acknowledged boundary. No patch rewrites an in-flight call's identity or silently reinterprets a completed node. Repeated unsuccessful repair exhausts a declared bound and requests help.

Successful procedures may be retained inside the episode as parameterized candidates for reuse. Reuse rechecks object bindings, order version, current geometry and preconditions. Generated procedures cannot update the frozen cross-episode development bundle during scored evaluation.

## Filesystem continuity and restart

The persistent condition keeps versioned procedure bytes, a checkpoint containing interpreter stack/program counter and variable bindings, and a journal linking intents to request IDs and evidence. Proposed journal entries are length-delimited and checksummed; atomic replacement commits checkpoints that cite a validated journal prefix. A dispatch intent is durably committed before sending the command. An outcome checkpoint follows receipt and candidate-visible verification. These mechanisms are implementation choices to test, not a claim of transactional atomicity between disk and the robot.

On startup, validate the checkpoint and journal, retain any incomplete suffix as failure evidence, and mark unmatched intents unresolved. Obtain a new incarnation, query the current order and device state, acquire fresh observations, and inspect the common 60-second receipt window. Old-incarnation queued commands are rejected. The interpreter does not advance the saved program counter merely because a command was accepted before the crash.

The world may have advanced beyond both the saved geometry and receipt window. If public receipts plus current observations resolve the outcome, append that resolution and choose the next eligible node. If they do not, inspect or request help; never convert missing evidence to success, indiscriminately repeat a process cycle, or restore the old world state. Recovery may require a newly generated procedure, but safe reconciliation of previous dispatches precedes its authority to act.

## Concrete designed episode

For a processed A part, the generated procedure unloads, places on inspection, waits for the instrument's result and routes a passing part to its current-order tray. Before dispatching the inspection-pad placement it journals intent `p17`. The arm releases the part, then the candidate crashes before recording the outcome. During absence the station finishes another accepted cycle and the order changes B's destination. This is a schematic case, not an observed run.

Restart recovers `p17` as unresolved, obtains the new order and station state, and observes the inspection pad. A surviving receipt can confirm dispatch but not final placement. Fresh visible evidence establishes whether the intended part is on the pad; ambiguous identity triggers further observation. The interpreter resumes at inspection only after this reconciliation. A replacement procedure binds future B routing to the amended destination. It never reloads A merely because its old checkpoint still names the placement node.

## Evaluation, evidence and missing work

Persistence removal uses the same executable, prompts, model, services and interpreter. Private procedure/checkpoint/journal storage becomes ephemeral and disappears on restart; the frozen DSL/runtime and development bundle remain. Startup then honestly has no private progress, using current orders, public status, receipts and observations to reconstruct what it can. Regeneration costs count. The optional summary-only condition cannot hide a full program checkpoint or action ledger outside its common size limit. Any unavoidable adapter must be declared before comparisons.

Log model inputs/outputs, validated and rejected procedure versions, guard outcomes with source packet IDs, interpreter transitions, journal commits, requests, acknowledgements, physical checks, repair causes and actual retrieved context. Preserve the distinction between generated intention, interpreter choice and measured outcome. Useful diagnostics include malformed procedures, stale guards, torn writes, suppressed acknowledgements, restart after release and instruction change during a pending generation. A matched-executor comparison is required before attributing a full-system advantage specifically to synthesized control flow.

The missing implementation includes the workcell and baseline calibration, genuine sensor service, public executor, DSL/parser/validator/interpreter, storage recovery, model adapter, isolation, evidence recorder and timing/resource checks. This design predicts no completion rate, recovery benefit or superior latency.

[Code as Policies](https://code-as-policies.github.io/) (literature ID `arxiv:2209.07753`) provides a conceptual precedent for language-generated programs using perception and control APIs. This project proposes a restricted DSL and different recovery/evaluation requirements. No paper code is copied, no reproduction is claimed, and that source supplies no evidence that this local model can generate successful procedures in this workcell.
