# Conditional PERSIST production evidence requirements

2026-09-27. **Design only: no production adoption, implementation, assessment change, benchmark, or new qualification.** Root is separately evaluating a bounded PERSIST/FULL prototype. Host-probe004 passed its declared criteria under instrumentation-only dev009; that observation neither attributes nor resolves probe003's I/O stall. All physical/model final qualification remains held.

These requirements apply only if root later adopts the candidate after reviewing prototype parity, recovery, space and timing evidence. They preserve FULL synchronization, the existing single SQLite connection and owner lock, original SQL/transaction grouping, commit-before-return ordering, image availability/retention, quotas and strict timing criteria. No weaker sync mode, asynchronous acknowledgment or additional writer is proposed.

## Current code establishes the integration points

[InstrumentedRecorder](../harness/instrumented_recorder.py) calls the original constructor before wrapping its one connection with `TimedConnection`. Its guard, recording and close methods delegate to the [original Recorder](../../../Storage%20Retention%20Implementation%20001/future/recorder.py). Those original sources must remain preserved. The instrumentation records elapsed phases; it does not currently provide a configuration/sidecar integrity receipt.

`Recorder.event()` commits referenced objects and the event before updating `last_durable_event`, then runs the physical guard. `image()`, `document()` and flushed motion commit before returning. The [FutureEvidence](../../../Storage%20Retention%20Implementation%20001/future/runtime_adapter.py) owner lock serializes those operations. The current bridge calls `image()` before returning the unchanged sensor result. A commit or quota failure must propagate through that existing path before a successful return/public observation update.

`_physical_guard()` counts `page_count * page_size`, excluding journal bytes. `close()` commits final state, closes SQLite, hashes/compresses the standalone database, verifies exact restoration, durably publishes gzip and manifest, then removes the working database. Both points need explicit prospective sidecar handling if PERSIST is adopted.

## Proposed protected receipt and independent checks

Use a separately versioned protected receipt, for example `recorder-policy.json` with a prospective `rci-recorder-policy-1` schema. These names are a proposal, not an implemented contract. Bind its path/hash in the host result and retain all referenced artifacts under the protected evidence root.

Report what was observed; do not infer a patched engine merely from package names. |

No receipt field such as `passed=true`, `policy_unchanged=true` or `single_connection=true` is sufficient on its own. The verifier must check the concrete readbacks, identities, ordering, retained bytes and failure receipts. Any detailed per-commit ledger must be bounded, independently hash-bound, and included in timing/storage qualification; do not add a second durability sync to every commit merely to create that ledger without assessing the resulting behavior.

## Sidecar and recovery boundaries

PERSIST commits by invalidating the rollback-journal header rather than deleting the journal. SQLite documents retirement through its own DELETE-mode transaction; do not unlink, rename, truncate or zero a potentially hot journal manually. Preserve the paired database and journal on failure, record incomplete status, and let SQLite perform recovery on a retained working copy before diagnosis. A successful process-kill recovery test is not a power-cut guarantee. [Official persistent-journal lifecycle](https://www.sqlite.org/atomiccommit.html#persistent_rollback_journals), [hot-journal recovery](https://www.sqlite.org/lockingv3.html#hot_journals)

`journal_size_limit` constrains the journal left after transactions; it is not a bound on growth during a transaction. Neither post-commit stat calls nor the existing sparse external monitor prove that transient peak. A proposed hard space claim needs a justified conservative transaction/sidecar bound or explicitly sufficient observation coverage. Include main database, journal, gzip temporary and published representations during overlap. Preserve the existing quota/reserve envelope and fail before an unbounded operation; do not silently enlarge limits to accommodate duplication. [Official size-limit semantics](https://www.sqlite.org/pragma.html#pragma_journal_size_limit)

FULL remains mandatory. Its readback confirms the selected SQLite policy, not universal physical power-loss durability beyond SQLite's filesystem/VFS assumptions. The original rollback/FULL caveat remains. [Official synchronous guarantees](https://www.sqlite.org/pragma.html#pragma_synchronous)

## Qualification and admission consequence if adopted

Fresh qualification would need exact logical/encoded content and image-availability parity; commit/rollback/guard/finalization failure propagation; retained-journal recovery; reader-compatible final gzip/manifest bytes; complete sidecar accounting; and unchanged strict timing under the actual workload. Existing byte-parity tests should distinguish exact recovered payloads from physical SQLite/container bytes, which must be authenticated for the new attempt and cannot be assumed equal across changed journaling behavior.

A future independent `recorder_integrity_pass` gate should propagate through host-probe, native, smoke, pilot and admitted assessment. Missing policy evidence, wrong sync mode, premature acknowledgment, unaccounted space or finalization/recovery ambiguity must be a severe infrastructure/evidence stop, never an ordinary numeric timing invalid or a robot task failure. This would require explicit future verifier/admission/settlement work and a new frozen release; none is implemented or authorized by this note.
