# Storage placement remains unadopted

Read-only follow-up to [native003](native-003-analysis.md), September 27 PDT / September 28 UTC. The failed windows include protected-journal fsync waits. This identifies the synchronous operation, not the operating-system, filter-driver, scheduler or device cause.

The [host inventory](storage-placement-inventory-001.json) found C: on a healthy NVMe SSD with NTFS and D: on a healthy USB SanDisk Extreme SSD with exFAT. Each reported more than 400 GB free. These are existing devices; no configuration, mount, ACL or filesystem was changed.

`Get-Acl` on the current C: campaign evidence and Windows workspace roots reports owner `AGENTPUTER\cresp` and an inherited `CodexSandboxUsers` ReadAndExecute grant (1179817), with owner/SYSTEM/Administrators FullControl. D: reports owner `Everyone` and an Everyone Allow rule of -1. Raw D: therefore does not reproduce the existing Windows protection on authoritative records. Microsoft documents that exFAT does not provide NTFS-style persistent ACLs and owner tracking. [Filesystem comparison](https://learn.microsoft.com/en-us/windows/win32/fileio/filesystem-functionality-comparison)

The existing isolated model namespace hides `/mnt/d`; that remains useful but does not demonstrate equivalence after removing another existing protection. The actual writable model workspace remains the Linux `/var/tmp/robot-codex-session10` namespace. `runtime_workspace` on Windows is the host's public mirror, not that Linux workspace. Moving only the mirror would not move all inference-related I/O. [WSL permissions](https://learn.microsoft.com/en-us/windows/wsl/file-permissions)

A possible fixed C,D,D,C synthetic journal diagnostic was considered, then not pursued after this protection gap was found. **No storage-feasibility prototype, plan, manifest, frozen revision, job, D: directory or output was created.** A latency result alone would not make raw exFAT an equivalent protected destination. No SQLite mode, sync policy, power setting, security exclusion or timing threshold changed.

If a suitable protected destination is established later, source preparation and evidence/workspace paths must be declared prospectively. Existing host launchers accept explicit paths, but preparers/coordinators currently choose C: roots. The native/host-probe receipts currently sample free space on the repository volume; every actual output volume would need coverage. Storage policy/baseline and independent admission must cover both all watched roots and all their volumes, with stable nonzero file identities. Same-volume temporary/final publication, actual namespace canaries, source lineage, full fresh qualification and unchanged durability remain necessary. Identical fsync calls alone cannot prove identical filesystem/device behavior. [Windows FlushFileBuffers](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-flushfilebuffers), [SQLite synchronization limitations](https://www.sqlite.org/howtocorrupt.html#failure_to_sync)

Campaign 002 remains authorized but unstarted. The next engineering work is a material correction to protected synchronous-I/O latency that preserves control, evidence and durability, followed by a fresh complete qualification. Do not resubmit native003 or select another unchanged run until one passes. No new human launch approval is requested or required by this note.
