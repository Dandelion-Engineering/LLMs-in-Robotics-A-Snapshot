# sustainable-evidence-3 physical and reader contract

The writer emits version 3 in SQLite `meta.version` and the close manifest. The current reader explicitly accepts versions 1, 2 and 3, and requires matching metadata/manifest versions. The preserved version-1 and version-2 readers under `history/` refuse version 3. Unknown versions, failed/unclosed stores and container hash mismatches are refused. No existing historical container is rewritten.

Version 3 retains the exact version-2 binary object encoding below and adds the `sqlite-gzip-1` finalized storage envelope. `evidence.sqlite` is a working file capped at 512,000,000 bytes, independently of any larger caller quota. Close streams it through gzip in 1 MiB blocks, flushes/fsyncs it, then independently decompresses the entire package and checks the exact original database byte count and SHA-256. The package and a separately written/fsynced manifest are durably published before the working database is removed: Windows uses `MoveFileExW(MOVEFILE_WRITE_THROUGH)`; POSIX also fsyncs the containing directory after rename. The complete manifest authenticates both compressed and uncompressed bytes/hashes. An interruption can safely leave both representations. A close/compression/publication failure preserves the working database where available and marks the recording failed; a published manifest cannot override a failure marker.

The working database plus finalized package have a hard disk overlap cap of 1,025,000,000 bytes for one writer, within the campaign's existing 2 GB temporary allowance. This applies to sequential queued execution; extra concurrent writers require additional reservations. Version-3 readers verify the package hash before restoring its exact bytes into an in-memory SQLite connection with queries only. Restore is capped at 512 MB of input buffer plus a SQLite copy of at most 512 MB, with 1 MiB streaming blocks and a separate encoded-object cache capped at 64 MB. No reader disk file is created. These bounds are per open reader, not a claim about the memory used by callers that retain all decoded events. Versions 1 and 2 remain read-only file-backed SQLite.

| Table | Contents | Integrity / ordering |
|---|---|---|
| `meta` | Format/run identity, declared image policy and recording state | Whole-container close hash |
| `events` | Binary exact event envelopes | Insertion order; nested content hashes; original event/payload identities remain inside envelopes |
| `objects` | SHA-256-keyed compressed binary values | Hash of uncompressed encoded node, including references to children |
| `telemetry` | Unique exact binary samples with integer row IDs | Per-row content hash; IDs are storage addresses, never substituted for acquisition sequence |
| `motion` | Compressed chunks of all supplied numerical rows | Per-chunk SHA-256; chunk order and original per-row times/gaps |
| `images` | Every offered capture ID/time/status/reason; optional paired encoded blobs | Whole-container metadata hash, paired RGB/depth hashes when available |
| `documents` | Named manifest/result/checkpoint/raw-request objects | Typed values and shared object references |

All binary length prefixes are unsigned little-endian 32-bit integers. Scalar tags are `n` (null), `t`/`f` (boolean), `d` (8-byte little-endian float64), `i` (length-prefixed ASCII integer), and `s` (length-prefixed UTF-8 with surrogate-preserving encoding). Float64 conversion is lossless for accepted JSON floats; nonfinite values are rejected. `l` is a length-prefixed value sequence; `o` is a length-prefixed sequence of string-key/value pairs. A Python tuple supplied by a native component has the same JSON-array semantics as frozen `json.dumps`. Object key order is retained by the encoder, although exact-object compatibility does not require a historical textual JSON layout.

`R` followed by 32 bytes references the exact SHA-256 object key. The object table uses zlib level 3. Version 1 eagerly interned nodes of at least 192 encoded bytes; version 2 uses the larger declared `INTERN_BYTES` threshold to avoid random-hash/page overhead from unique tiny nodes. Envelopes below that threshold use `Z`, a length-prefixed zlib-compressed binary node. Interning is a physical optimization, with no change in decoded content. Related object families can use a standalone anchor's last 32 KiB as a zlib dictionary. Such object payloads begin with `D` and the anchor's 32-byte object hash. Anchors never depend on another anchor, and the writer holds at most 128 dictionary tails (4 MiB) in memory. Both dictionary and content hashes are checked while reading.

`T` contains a count followed by `(uint64 start_row_id, uint32 count)` spans. Adjacent row IDs are coalesced only when they name precisely the supplied ordered samples. An arbitrary gap/order/repetition is represented with more spans; no time-based inference is used. The decoder validates every referenced row and expands spans in order. Version 2 uses `V` for a shared exact field-name sequence followed by its full-precision values. Telemetry is keyed by the complete reconstructed binary row, including timing/sequence/gap metadata. When a window has one consistent key order, stored rows use sorted keys and `U` records the original field-name order plus the exact `T` spans. Thus textual JSON with sorted keys can reference the same numerical samples as structured public packets, while each occurrence reconstructs its original key order. Heterogeneous key-order windows retain separate exact rows.

`J` stores an exact JSON-text recipe and a recursively encoded JSON value. The recipe records leading/trailing whitespace and the specific `json.dumps` formatting parameters. The writer uses it only when that formatting reproduces the original string character for character before storage. Duplicate keys, unmatched escaping/number syntax, irregular formatting, non-JSON text, and strings outside the bounded recipe-size limit fall back to opaque exact strings. No normalized model prompt or checkpoint replaces an original string. The reader returns the reconstructed string, not the parsed object. This allows model/checkpoint JSON text to share canonical telemetry/object content while retaining exact text and file bytes.

Motion chunks contain an encoded list of complete rows. They have a maximum of 1,000 rows by default. Every float, contact/safety field, target, flag, unknown field and missing value supplied by the runtime survives. No schema projection to only the current 32 diagnostic values occurs. At close the remaining chunk is committed. Incomplete stores are unavailable for complete scientific claims.

The ring stores paired encoded RGB/depth only in bounded memory. Sparse, representative and triggered selection persists the original offered pair, with no resizing or lossy recoding. Live arrays/response bytes are delivered independently. The actual live raw-request wire encoding is retained as core evidence when a candidate requested it; its bytes can be scientifically material even when that camera time was not selected for general imagery.

`Reader.events()`, `motion()`, `document()`, `images()`, `image()`, `require_images()`, and `package()` are the version boundary. They do not expose candidate read access. Existing numerical/continuity functions receive their canonical objects through these iterators. The selected-image package emits explicit availability, and refuses an unknown capture identity. `available` with a bad hash is corruption; `unavailable_by_policy` is intentional absence with a policy/quota reason. They must remain distinct in any future UI.

Storage failures invalidate the attempt. Optional imagery can reach its declared cap with explicit unavailability; mandatory representative selections cannot. Core evidence never silently truncates or lowers precision. The supervisor stops on `RecordingFailure` or I/O failure. The failure marker is a bounded control record outside the scientific quota. Failed evidence is retained for diagnosis but cannot pass the complete-container reader.
