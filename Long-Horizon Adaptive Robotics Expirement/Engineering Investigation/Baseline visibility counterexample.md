# Scheduler visibility-budget counterexample

This is source analysis and a synthetic public-packet counterexample. It is **not a diagnosis of C0-007**. Root's partial monitoring reported a halted candidate, no pending action/error/failure counts, nine completed-looking records and B6 last known raw/unprocessed. That does not establish B6's visibility, mark, actual physical location, or the triggering help reason. The whole development batch was still active when this investigation was prepared; no pending raw evidence was read.

Run the retained [counterexample](baseline_visibility_counterexample.py) from the project root:

```powershell
.\venv\Scripts\python.exe -X utf8 -B "Long-Horizon Adaptive Robotics Expirement/Engineering Investigation/baseline_visibility_counterexample.py"
```

It imports the actual candidate policy and mocks only persistence/directory operations. It writes nothing, calls no queue or simulator, and reads no run evidence. It hashes the Runtime source before/after. Nine synthetic parts have retained completed-cycle/passing-inspection proof and fresh detections in the required trays. The remaining B6 has a fresh raw-zone detection but an **unknown** visual process mark. B6 is simply a public fixture label, not a policy special case or a hidden-state hint.

Five candidate steps using the same camera sequence 100 produce `observe, observe, observe, observe, help`. `_idle_steps` becomes 4 and `halted` becomes true. A subsequent new camera packet that clearly reports B6 as raw still returns `wait`, although calling the scheduler alone would select its transport into the compatible fixture. A new, previously unseen human-answer ID clears the halt and the normal step returns that transport. All assertions pass against the inspected source. No physical completion is simulated or claimed.

Relevant source behavior:

- [Candidate ingestion](../Runtime/candidates.py) rebuilds `_visible` on every packet (lines 245–286). Accepted detections require finite age in `[0, 1.5]`, recognized part family/zone/kind and finite position. Retained `last_seen` is separate and can outlive visibility. Neither a current eligible raw part nor a current completed-tray count follows from retained records alone.
- `_counts` uses current visible tray detections plus retained process/inspection proof (587–596). Raw stock selection (674–684) requires a currently visible required-family raw/parking part, `visible_mark == raw`, and no retained cycle. An absent/stale detection or unknown mark cannot enter that branch. An earlier inspection/tray/fixture branch can take priority.
- The fallback (687–689) issues observations while `_idle_steps < 4`, then help. `_issue` increments `_idle_steps` on **every issued observe or wait**, not each distinct fresh image (981–984). Successful pending reconciliation resets it (353–356); a newly received human answer resets it too (306–323). It is an in-memory attribute, not a checkpoint field, so exact history must be reconstructed from actions/resolutions/answers.
- Issuing help immediately sets the durable halt flag. `step` still ingests and reconciles packets, but with no pending action then returns wait while halted (1023–1028). Fresh stock alone does not clear it. A repeated already-received answer ID does not clear it; a new answer does. This permits repeated visibility/help rounds without supported productive progress.
- [Supervisor dispatch](../Runtime/experiment.py) can dispatch steps using the latest available observation without requiring its camera sequence to differ from the prior step (845–847). Normal observe completes as a no-motion action in [Cell](../Runtime/cell.py), lines 573–576; it does not require a new image before acknowledging. The regular camera pipeline remains independent. Therefore the repeated-frame synthetic input is permitted by these interfaces, though its occurrence in C0-007 is unverified.
- Scripted assistance waits for at least 15 seconds on both simulation and wall clocks, retains each answer, and performs no physical rescue (`experiment.py`, 300–336). A monitored halt may be a pending assistance interval or a repeated exhausted round; the exact events decide.

After official batch completion, extract only the exact help/action and packet window first. Retain help reasons and request IDs; parent-linked candidate input/reply; preceding observe/wait actions back to the last successful resolution/new answer; packet incarnation/sequence/capture time/current time; B6 detection **or explicit absence**, mark/zone/age/family/kind; all visible-part summaries, order counts, station and gripper. Keep canonical/raw task results separate. Match help acceptance, answer creation, actual answer delivery, and `public_human_answer_received` events. Then inspect the source-linked image and protected B6 final/near-halt state separately to distinguish physical displacement or persistent occlusion from transient image freshness. Full-stream extraction is a later queued, receipt-bound task.

Minimal proposed shared fix, to review after the actual incident window is available:

1. Treat visibility reacquisition as an explicit bounded state. Charge its existing observation budget only when a **distinct fresh camera capture** is delivered after the request; repeated step packets and ordinary machine waits must not consume it. Use existing public capture sequence/time and the existing freshness rule, without creating a new numerical threshold.
2. Reset that budget on supported productive action reconciliation. Keep public order changes and materially newly available action evidence explicit; a new packet number, no-op observe receipt or repeated generic advice is not productive progress. A first new help answer may allow one labeled assisted reacquisition round.
3. Scope the pause reason to visibility. While this pause is active, continue reading public packets and resume ordinary policy selection when fresh evidence supports an admissible action. Do not clear pending-outcome uncertainty, held-recovery blocks, bounded physical-failure limits, or other halt reasons, and do not dispatch a recovery action by fiat.
4. Coalesce help within the unchanged no-progress visibility episode. After the bounded assisted round fails, retain an explicit blocked/unknown visibility reason and wait for new supported evidence; do not issue an endless stream of identical paid waits/help answers. Re-arm only after supported progress or a material public situation change. Preserve every original assistance request and its attribution.

The common observation/reconciliation bookkeeping should be available identically to all architectures; their action-selection policies remain responsible for their choices. The baseline and A3 share `_baseline_action`, while A1/A2 have distinct model/procedure selection, so a change must not quietly turn their fallback into the baseline scheduler. No protected truth, unseen-object assertion, target-ID special case, or Runtime edit is proposed here. The source counterexample warrants review of this bookkeeping; it does not prove that this change alone resolves the actual incident.
