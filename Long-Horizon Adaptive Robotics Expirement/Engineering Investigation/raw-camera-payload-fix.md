# Raw-camera payload failure and bounded repair

The actual `physical-calibration-001/raw-cameras` probe failed; its original evidence remains unchanged. The parent task verified the seven-probe execution job `20260923T050529437896Z-06e48539` succeeded with exit 0 and sources unchanged. A successful calibration driver exit does not override a failed probe.

[Events](../Evidence/calibration/physical-calibration-001/raw-cameras/events.jsonl) 31 and 37 contain passing independent native-byte/identity round trips for overhead and oblique respectively. Their outgoing wrapped IPC lines were 303,505 and 335,098 bytes. Event 41 records wrist capture sequence -3 at simulation 2.8899999999999033 seconds, with its exact camera calibration and original RGB/depth artifact hashes. Event 43 records the wrist response and decoder error.

The [retained wrist IPC](../Evidence/calibration/physical-calibration-001/raw-cameras/raw-wrist-ipc.json) is a 331-byte `payload_too_large` reply. Native RGB PNG is 63,457 bytes and native depth NPZ is 825,230 bytes. Their Base64 representation plus metadata exceeds the gateway's unchanged 1,044,480-byte limit. The fixture correctly rejects the status: `Raw response was not delivered: payload_too_large`. The driver's generic “no successful decoded camera evidence” error obscured that explicit size rejection. This is not evidence of camera corruption or a sandbox decoder failure.

The gateway now attempts one standard NPZ ZIP-LZMA lossless fallback only after the original deflated reply fails the same size check. Native image dimensions, float32 bits, capture sequence/time, camera calibration and capture identity remain unchanged. PNG/RGB encoding is unchanged. If the fallback still exceeds the limit, the response remains `payload_too_large`; there is no resizing, quantization, chunking or increased quota. Compression and artifact writes remain on the bounded raw encoding worker, with physics continuing.

The original deflated capture artifact remains separately identified and hash checked. A successful LZMA wire representation is written as a distinct `*-depth-lzma.npz` artifact. Operator `last_evidence.source_artifacts` names original capture encodings, while `last_evidence.artifacts` binds the actual transmitted encoding and SHA. `images.depth.npz_compression` declares `lzma`; it is still a standard `npz-base64` container holding the same `depth_m.npy` bytes. No changed archive is labeled as the original file. The normal SensorWorker and its automatic capture compression were not changed. The existing stdlib fixture already decodes standard ZIP-LZMA and required no policy/decoder edit.

A bounded offline check on the one retained wrist depth file reduced its NPZ from 825,230 to 125,371 bytes, taking approximately 0.17 seconds for compression plus decode on this host. Exact decoded NPY equality held for all 1,228,928 bytes, SHA-256 `03ad8e77202a91b00aa36695b79f8618b615fb902cc84ca9aadfe35fc981ba76`; source NPZ SHA-256 is `f4a5b4543957da886fc64c7a09c730bce538297702d6ed3ebe18970d8635ac5f`. Combined image Base64 payload would occupy 251,776 bytes before metadata. This is a retained-frame codec measurement, not a fresh camera or complete IPC/timing calibration.

Fixtures are synthetic and remain outside experiment evidence. No physics run, model call or queue job was launched for this fix.
