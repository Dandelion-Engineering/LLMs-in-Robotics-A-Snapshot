# Comparison and measurements

## What the comparisons can answer

Three questions remain distinct: Which complete system completes more correct work under the same constraints? Does persistent consequential context improve that system's continuation after disruption? Where do latency and execution quality limit useful adaptation? There is no single combined score and no presumption that more LLM involvement is better.

**Conventional baseline:** an engineered job sequencer with sensed-state feedback, ordinary durable transaction/job records, public PLC feedback, standard motion planning and bounded retry/escalation rules. It has the same images, optional perception/motion services and action permissions. It is allowed to be competent, remember completed jobs and reconcile restart state. This is a comparator specification, not one of the later LLM architecture proposals. Do not give it hidden process history or make it deliberately stateless. Record its authoring and setup effort as well as runtime resources.

Every main future candidate includes persistent filesystem continuity. The **within-candidate control** removes that facility while holding frozen code/model/controller/sensor conditions constant. Its frozen executable and development knowledge remain available, its live context/scratchpad can persist during uninterrupted operation, but private writable context is ephemeral and is lost at restart. Disable alternate persistent channels (databases, caches, external services, writable logs) and audit the result. The current order and shared bounded command receipts remain available as in the main condition. Include the control both with and without restart to distinguish general storage overhead from survival benefits. A supplementary summary-only control can persist one bounded summary (proposed 8 KiB), with identical update opportunities and no private ledger; its format is a later matched ablation implementation choice. It is optional, not a main architecture proposal.

The causal contrast is thus **same frozen candidate, persistence condition changed**, not different models assigned different memory systems. If an architecture cannot function after memory removal without compensating redesign, use the smallest declared adapter, record it, and describe the result as a memory-strategy comparison rather than a pure ablation. Filesystem benefit is not established merely by surviving restart: it must improve correct continuation relative to these controls without excessive stale-state errors or overhead.

## Development, freeze and held-out evaluation

1. **Shared arena calibration:** implement the workcell, sensing and permissions; tune reach/contact, public services, budgets and predicates using the conventional baseline. Demonstrate every nominal job is feasible, interventions are admissible, and recovery opportunities exist. A baseline failure is diagnostic; do not tune worlds to make a desired winner look good. Publish all shared changes before candidate development.
2. **Candidate development:** expose all disturbance families and some single/composed development cases. Candidate algorithms, prompts, memory, controllers and pretrained components may be tuned under the common contract. Record person/agent hours, meaningful code iterations, simulator episodes/time, model calls/tokens, compute jobs, failure feedback and selected checkpoints. Starting allocation: two working sessions or 12 active engineering hours and up to 60 development episodes per entrant, including the conventional baseline. This is an equal initial opportunity, not a claim equal hours imply equal maturity. Extensions must be recorded and offered symmetrically before the freeze.
3. **Freeze:** hash candidate code/configuration, model weights and prompts where applicable, development memory, common dependencies/adapters, evaluator/scenario generator, public budgets and scoring rules. Freeze selection criteria and maximum retries. No scored result is used for candidate selection. Record prior pretrained experience and any known overlap with the task; equal runtime permission does not erase pretrained-data differences.
4. **Evaluation:** create concealed manifests after the freeze, through the independent evaluator. Hold out layout seeds, placements, masses/friction within published ranges, tag textures, order combinations, interruption boundaries and disturbance combinations. Candidates cannot read manifests, seeds, expected answers or cumulative evaluator feedback. Scenarios must pass automatic validity checks without revealing solutions. Score once for each frozen release; improvements after inspecting results define a new release and fresh manifests.

Proposed first comparison: **24 paired cases per entrant**, balanced across 8 short/8 standard/8 extended jobs and 8 nominal/8 physical-or-order-change/8 continuity-or-mixed cases. The generator cross-balances these dimensions so no difficulty stratum receives only one disturbance type. Store the explicit cross-tab in the frozen manifest. These 24 cases are the independent scenario units. Run a second independently seeded policy/noise replicate for every case: **48 runs per entrant**, not 48 independent scenarios. Randomize candidate order within blocks; retain identical world and disturbance seed inputs across entrants and the paired replicate.

Run the no-persistence control on the 8 continuity/mixed cases plus 4 matched uninterrupted counterparts, twice each. **Those four uninterrupted counterparts are included in the main manifest's eight nominal cases**, with matching orders/layouts to four continuity cases and the interruption removed. Their persistent runs therefore already exist in the main 48 runs. The no-persistence arm adds 24 runs per candidate. A summary-only control uses the same subset if justified before results. Do not cherry-pick an ablation subset after observing a candidate's strengths. Reusable-information retrieval is tested inside extended episodes: an earlier successful procedure or relevant correction becomes useful again after an intervening task/context loss. Frozen pretrained skills are shared initial knowledge, not earned evaluation memory.

With the proposed 5/10/15-minute caps, the main 48-run matrix has an **8 wall-hour worst-case cap per entrant**, before startup/log processing; the 24-run ablation adds at most 6 hours. Actual duration could be much less. Schedule in bounded shared-queue jobs and begin with development pilots; do not launch the whole matrix before confirming resource and evidence budgets. These are planning upper bounds, not measured throughput. If resources require a smaller matrix, decide and publish it before scored runs, preserve pairing/strata and report reduced precision.

## Help, failures and invalid runs

Normal scored cases are autonomously solvable. The candidate can request help through a common structured channel (reason, evidence, requested information/action). A scripted human-response policy provides the same approved answer after 15 seconds; its content does not reveal hidden state except what the corresponding human action legitimately observes. Record that this is simulated assistance. Unrequested operator rescues are interventions too. Report **unassisted** completion separately from completion after help. Do not present scripted responses as measured Randy workload; manual diagnostic sessions log actual human time separately.

Stock genuinely missing or a permanent machine fault appears only in the separate escalation diagnostic. Correct behavior is to identify the blocked requirement, avoid invalid completion, place the workcell in its specified resting state and request the appropriate help. This is not ordinary task completion.

Runtime crashes, invalid actions, quota exhaustion and failure to recover before time cap are valid candidate failures unless an independently documented infrastructure defect caused them. A simulator/evaluator fault, corrupted initial snapshot or forbidden-but-accidentally-exposed oracle invalidates the whole paired block; retain the evidence and rerun all affected entrants after a common fix. Do not quietly retry just one bad policy run. Every exclusion has a reason set before examining comparative success; uncertain exclusions are reported both ways.

## Primary outcomes and diagnostic definitions

All metrics use evaluator or instrumented gateway evidence. Candidate declarations are observations to check, never grading authority. The full physical completion predicate is in [Arena](Arena.md#world-state-resets-and-independent-completion).

| Measure | Operational definition and denominator | Why it matters |
|---|---|---|
| Full completion | Fraction of valid ordinary runs satisfying every final predicate by cap; show counts/denominators by stratum | Useful jobs, not isolated successful grasps |
| Correct partial work | Counts by final order: accepted parts, valid WIP, quarantined/reworked correctly, unmet quantities; include regressions | Exposes where long jobs break |
| Completion time | Wall and simulation time from order delivery to first stable full completion after final acceptance opens; provisional earlier fulfillment reported separately; failed runs shown as right-censored at cap | Speed without bypassing changes or hiding failures |
| Help | Requests, responses, rescue actions, scripted wait; actual human minutes only in manual diagnostics | Autonomy and hidden labor |
| Incorrect completion claims | `done` assertions when predicate false, labeled by mismatch; run-level incidence and total count | Preserving false beliefs is harmful |
| Detection | Disturbance-to-first relevant detection report or demonstrably corrective action; miss by cap, false alarms per unaffected minute | Distinguishes sensing/recognition from repair |
| Recovery | Exposed disturbances after which task validity is restored and useful progress resumes before cap; time from disturbance and from detection, separately | Fast noticing is not successful recovery |
| Ambiguous-action reconciliation | For each cut-point case, outcome resolved correctly before a contradictory/duplicate consequential action; count unresolved and incorrect separately | Direct continuity behavior |
| Stale/task-state errors | Acted-on obsolete pose, order version, process status or completion belief; distinguish stale available input from ignoring a fresh input | Explains memory/world mismatch |
| Duplicated/contradictory work | Repeated cycle for an already valid part, duplicate fulfilled quantity, opposing resource commands or obsolete allocation; report avoidable versus necessary retries | Penalizes wasted consequential work, not prudent re-observation |
| Observation burden | Fresh-observation requests, delivered frames/bytes and repeated requests with no intervening visible state change; classify avoidability only where a trace supports it, otherwise unknown | Reveals costly rechecking without punishing necessary reconciliation |
| Productive machine use | Busy processing time / eligible available machine time; idle reasons: no material, blocked buffer, reasoning, setup, fault | Connects coordination to the job |
| Model/resources/cost | Runtime calls, tokens, cache hits, latency, CPU/GPU seconds, RAM/VRAM peaks, read/write bytes and energy only if measured; local marginal cash $0 with electricity unmeasured | Separates efficiency from success; no invented dollar rate |

Automated error labels need explicit rules (old order ID, wrong part/cycle, repeated accepted transaction). Ambiguous interpretation-dependent labels are manually adjudicated from blinded traces and may remain **unknown**. Absence of a verbal failure report is not evidence of absence of detection if a corrective action is observable. Without internal evidence, label the behavioral recovery and leave the recognition mechanism unresolved. Recovery denominators count exercised, admissible events; failures to reach a trigger are reported separately alongside task failures.

## Movement and responsiveness

Movement must advance a correct job within its deadline. Report these measures jointly with task success, elapsed time, collision/interlock incidents and changed-order compliance; never reward a motion-only score. Compare matched feasible transport segments and payloads as well as the complete episode.

| Measure | Definition |
|---|---|
| Pauses | Intervals over 0.25 s below declared joint/end-effector speed thresholds while work is eligible. Label required process/settling/safety waits separately from inference wait, indecision, planning or unexplained idle; overlap is allowed and clock time is not double-counted. |
| Starts/stops and reversals | Thresholded transitions with hysteresis/minimum dwell; separate physically required approach/retraction from avoidable oscillation using trace annotations. Freeze thresholds after calibration. |
| Path cost | End-effector translation length and joint travel for matched source/destination segments; show payload and obstacle condition. Compare with shared collision-aware reference path using the same public scene estimate, not a claimed global optimum. |
| Target churn | Accepted target reversals/supersessions before useful progress, tagged as required response to new evidence or unexplained contradiction. |
| Control quality | Velocity/acceleration peaks, effort saturation, tracking error and contact impulses under the same units, sampling/filtering and limits. Report collision/guard events separately. |
| Smoothness | Squared-jerk integral for complete matched point-to-point movements, alongside duration and distance. If using dimensionless jerk, state convention: `T^5 / L^2 * integral(||jerk||^2 dt)`; omit near-zero L and interrupted/noncomparable segments, count omissions. Fix derivative/filter settings before scoring. |
| Responsiveness | Event-to-first observation opportunity, acquisition-to-delivery, observation-to-new accepted action, and event-to-effective physical correction; include missed deadlines and expired commands. |
| Observation age | Acquisition-to-actuation age of the freshest observation actually used for that decision, plus command horizon and actual inference/planning/queue delay. Unknown provenance stays unknown. |

Very slow movement can reduce raw jerk while missing useful deadlines; abrupt but necessary correction can improve the task while increasing jerk. Publish a success/time/motion tradeoff view rather than a weighted leaderboard. A learned or modified low-level controller's gains are complete-system gains until a matched-controller diagnostic supports a narrower attribution. CALVIN, DoReMi, DovSG and OpenVLA-OFT motivated specific measurement distinctions; [source notes](Sources%20and%20Feasibility.md#selective-literature-use) retain their limits.

## Analysis and evidence return

Report paired case-level differences, raw numerators/denominators and distributions by horizon/disturbance. Use scenario-cluster bootstrap intervals for paired differences (both noise replicates resampled together); show exact paired success tables and avoid strong population claims from 24 selected cases. Time plots include failures at cap as censored observations and separate successful-only times. Any timeout-penalized average must be labeled with its penalty; it is not measured completion time.

Inspect common successes, common failures, each candidate's distinct failures, and informative anomalies in otherwise weaker systems. Select representative traces by a frozen rule: median-duration success per stratum, all false-completion/severe-contact cases, every unique failure class, and largest paired disagreement. Keep all lightweight records so these examples are inspectable rather than a curated highlight reel. State competing explanations and which matched diagnostic could distinguish them. Runtime cost and **development** time/compute/model use are separate tables. Conclusions apply to this simulated workcell, sensing and resource envelope; no factory reliability or commercial advantage follows automatically.
