# Shared queue limitation discovered during Batch 01

The installed shared queue was inspected read-only. Its `pid_alive` function calls `os.kill(pid, 0)` at line 52. On Windows, Python's documented behavior for signals other than CTRL_C_EVENT/CTRL_BREAK_EVENT is process termination, rather than the Unix-style liveness check. See [Python 3.12 os.kill](https://docs.python.org/3.12/library/os.html#os.kill).

This matters in `ensure_worker`, worker-lease acquisition, stale-lock checks and doctor/repair paths. Concurrent submission of the Panda asset job while the model download's worker existed coincided with the model attempt being marked interrupted. The original worker and child were still observed alive, then that model-owned orphan process tree was stopped; its worker subsequently recorded failure. These observations and source inspection support a queue defect, not a model failure. The first model attempt `20260923T021802525938Z-3fb5a00d` is not successful installation evidence.

The queue and its runtime state were **not modified**. This project currently submits only when the preceding worker has naturally exited, observes active jobs through their own log and OS process state, and performs the required official `status` query after exit. Successful asset acquisition: `20260923T021828928716Z-80c61bb5`; successful model retry: `20260923T022323173828Z-4b96b624`. Both were verified as `succeeded` with exit status 0.

This operating constraint is not a queue repair or a guarantee against another project's concurrent submission. The owner of the shared Dandelion queue should replace the Windows liveness implementation with a non-destructive process-query API and test concurrent submit, status/lock contention, cancellation and worker-loss recovery. Under this project's instructions, that maintenance belongs to the queue's owning workflow. A resulting infrastructure interruption must remain visible and cannot be reclassified as a candidate failure or used to select a preferred architecture.
