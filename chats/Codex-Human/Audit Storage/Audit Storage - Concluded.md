# 7. Implement a Sustainable Recorder for Future Releases

The existing r4 cleanup solves the immediate disk crisis. It does not solve future growth by itself.

Create a **new versioned evidence-recording design and implementation** for future releases. Do not retrofit it into frozen r4.

The future recorder should preserve the scientific capabilities described in `Sustainable Retention.md` while avoiding the “persist every live packet in expanded form” strategy.

## A. Separate live sensing from image persistence

The robot/candidate may still receive whatever live RGB/depth rate the experiment requires.

Permanent storage should be independently controlled.

Implement a bounded policy with:

- a sparse declared RGB/depth stream appropriate for later inspection;
- paired RGB/depth when visual perception verification matters;
- a bounded rich ring buffer;
- triggered pre/post windows around important events/failures;
- selected representative runs/traces;
- bounded outcome-selected anomaly windows;
- explicit frame-availability metadata.

Do **not** write full 10 Hz image/depth streams for every run and then plan to delete them afterward.

The persistence policy must not change what the candidate was allowed to observe.

## B. Store repeated structured content once

Design a versioned canonical representation where repeated information is stored once and referenced.

At minimum investigate and implement an appropriate representation for:

- 100 Hz telemetry/numerical samples;
- observation packets that reference exact ordered telemetry ranges instead of embedding the same sliding window repeatedly;
- candidate-input packets that reference already-recorded public observations instead of embedding duplicate copies where possible;
- model request/context objects;
- model responses;
- checkpoint/file contents;
- repeated public/device state objects.

Preserve:

- exact event identity;
- parent/causal links;
- acquisition/delivery times;
- model-call timing;
- command timing;
- restart semantics;
- missingness;
- stale-data identity;
- exact model/file content needed for investigation.

A compact format may use binary/typed chunks plus reference envelopes if that is more appropriate than JSONL.

Do not optimize for human readability of the raw file at the cost of hundreds of gigabytes. Human-readable adapters/viewers can sit on top.

## C. Preserve full-precision numerical evidence

Do not solve the storage problem by silently reducing the 100 Hz numerical information required by the current motion/jerk/pause/tracking diagnostics.

The audit estimated that the currently consumed 32 float64 values at 100 Hz over the full planned task cap matrix are roughly 4 GB before metadata.

Use an efficient representation, but preserve the required numerical precision, timing, gaps, and diagnostic fields.

Any downsampling or lossy encoding requires a separate scientific decision and is not authorized here.

## D. Versioned compatibility readers

Current analysis and investigation tools should not have to know every physical storage detail.

Create a clear versioned reader/adapter boundary that can expose the canonical evidence needed by:

- analysis;
- diagnostics;
- continuity;
- selected trace packaging;
- investigation viewers.

For the new format, require semantic/exact-object reconstruction of the candidate-visible packets and recorded model/file content.

Do not pretend the new future-native format must reproduce the literal historical r4 JSONL bytes.
